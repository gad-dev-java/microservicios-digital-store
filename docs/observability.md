# Logging y trazabilidad

Especificación para HT-08. La instrumentación y los tests descritos aquí se incorporan al implementar esa historia; las migraciones V1 ya reservan `traceparent` y `tracestate` en `outbox_events` y `email_deliveries`.

## Correlación entre servicios

- Usar Micrometer Tracing y W3C Trace Context. Gateway inicia una traza si la solicitud no trae `traceparent`; Catalog y Order continúan el contexto recibido. Las llamadas HTTP salientes se construyen con el `RestClient.Builder` configurado por Spring para propagar trazas. En local, configurar muestreo al 100 % para la demo; dejar la probabilidad configurable para un despliegue futuro. No hace falta un visor ni exportar spans para correlacionar los logs. [Tracing en Spring Boot](https://docs.spring.io/spring-boot/reference/actuator/tracing.html), [W3C Trace Context](https://www.w3.org/TR/trace-context/).
- El webhook de Mercado Pago inicia **otra traza**: el proveedor no continúa la del navegador. Relacionar checkout, webhook y pedido mediante `orderId` y `paymentAttemptId`; nunca interpretar el `traceId` como identidad del comprador ni como clave de idempotencia.
- Al escribir el outbox, capturar el contexto vigente en `traceparent` y, si existe, `tracestate`. El relay restaura ese contexto al reclamar la fila y publica con observación de `KafkaTemplate` activada, para inyectarlo en los encabezados Kafka. Notification activa observación en el listener; al crear `email_deliveries` conserva el contexto para que el scheduler de correo lo restaure al enviar. Si falta contexto, iniciar una traza nueva y conservar `orderId`/`eventId` en los logs. [Observación en Spring Kafka](https://docs.spring.io/spring-kafka/reference/kafka/micrometer.html).
- La correlación llega hasta el registro del envío SMTP. Mailpit muestra el correo, pero no participa automáticamente en la traza. El Gateway usa WebFlux: confiar en la instrumentación y el contexto reactivo, sin basarse en un hilo fijo ni copiar MDC manualmente entre hilos.
- Si un caso de uso incorpora `@Async`, configurar un `TaskExecutor` con propagación del contexto de Micrometer y comprobar que la traza continúa en el hilo de trabajo. Copiar solo el MDC no restaura necesariamente el contexto de traza. Los schedulers de outbox y correo restauran explícitamente el contexto persistido, no el de una petición HTTP ya terminada. [Observabilidad en Spring Framework](https://docs.spring.io/spring-framework/reference/integration/observability.html).

## Reglas de logging

Usar SLF4J con parámetros `{}`. Registrar en `INFO` cambios de estado relevantes (pedido creado, pago confirmado, evento publicado, correo enviado), en `WARN` fallos recuperables y en `ERROR` fallos agotados o inesperados. Registrar cada fallo una sola vez en el límite que lo gestiona; los objetos de dominio no generan logs. Incluir identificadores técnicos (`orderId`, `eventId`, `paymentAttemptId`, `deliveryId`) cuando existan; Micrometer añade `traceId` y `spanId` al contexto de log. Nunca registrar JWT, secretos, correos, nombres, datos de pago, cuerpos completos de peticiones ni rutas de archivos. No aceptar `userId` ni otros campos de log desde cabeceras o `baggage` aportados por el cliente; si se añade un identificador de usuario, derivarlo solo del JWT validado. Desactivar `hibernate.show_sql` fuera del diagnóstico local. El `traceId` se añade a `ProblemDetail` cuando HT-08 esté implementada.

## Salud y verificación de HT-08

Mantener `/actuator/health` e `/actuator/info` en la red local. Gateway solo expone su propia salud en el puerto ligado a `127.0.0.1`; no enruta los Actuator de Catalog u Order. Comprobar que una llamada Gateway → Order/Catalog conserva `traceId`, que webhook → outbox → Kafka → Notification conserva el de la traza del webhook y que el scheduler de correo lo recupera. Verificar la separación de trazas del webhook, la ausencia de datos sensibles en logs y que un contexto ausente no impide procesar el evento. Los timeouts HTTP y el Circuit Breaker siguen las reglas de [architecture.md](architecture.md).
